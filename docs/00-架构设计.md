# AgentForge 企业级 Agent 平台 · 总体架构设计

> 版本 v1.0 ｜ 阶段：P0 架构设计 ｜ 最后更新：2026-08-19

## 一、平台定位与能力边界

AgentForge 是一个**企业级 Agent 应用平台**，为组织内部提供「可编排、可扩展、可审计」的 AI 智能体运行环境。

### 1.1 核心能力

| 能力 | 说明 |
| --- | --- |
| 多轮对话工作台 | 流式输出、工具调用过程可视化、思维链折叠 |
| Agent 编排引擎 | 基于 LangGraph 的状态机编排，支持中断/恢复/人工介入 |
| MCP 工具生态 | 标准 MCP 协议接入外部工具，动态注册与发现 |
| Skill 技能系统 | 渐进式披露的技能包，按需加载领域知识与工作流 |
| 代码执行沙箱 | 进程级隔离 + 资源限额，安全执行模型生成的代码 |
| RAG 知识库 | 文档解析、向量检索、引用溯源 |
| 企业级治理 | RBAC 权限、Token 配额、全链路审计、成本分析 |

### 1.2 明确不做的事（能力边界）

- **不做模型训练/微调**：平台是模型消费方，通过统一网关接入外部模型
- **不做通用 IDE**：沙箱只服务于 Agent 的代码执行需求，不是在线编程环境
- **不做多租户 SaaS（v1）**：v1 定位单组织私有部署，但数据模型预留 `tenant_id` 字段

> **设计经验**：明确写下「不做什么」比写「要做什么」更重要。需求边界模糊的项目，最终都死于无限膨胀的功能列表。

## 二、五层架构

```
┌──────────────────────────────────────────────────────┐
│ 接入层  Vue3 控制台 · 网关鉴权限流 · SSE 流式通道       │
├──────────────────────────────────────────────────────┤
│ 业务层  认证 RBAC · 会话消息 · 工具技能注册中心          │ SpringBoot 3
├──────────────────────────────────────────────────────┤
│ 智能层  状态机编排 · 上下文管理 · 模型路由               │ Python LangGraph
├──────────────────────────────────────────────────────┤
│ 能力层  MCP 工具 · Skill 技能 · 执行沙箱                │
├──────────────────────────────────────────────────────┤
│ 数据层  MySQL 业务 · PostgreSQL 向量 · Redis 缓存       │
└──────────────────────────────────────────────────────┘
```

### 2.1 为什么智能层必须独立进程

这是本架构最关键的一个决策。把 LLM 调用写进 Java Service 层能快速跑通，但存在三个致命问题：

**（1）生命周期不匹配**

业务接口是毫秒级请求-响应模型，Tomcat 线程池按此假设配置（默认 200）。Agent 任务是分钟级长流程，一个跑 3 分钟的任务会独占线程。200 个并发 Agent 就能打满线程池，导致登录、鉴权等基础接口全部不可用。

虽然可以用 Servlet 3.0 异步 + 虚拟线程缓解，但仍然无法解决下面两个问题。

**（2）变更频率差一个数量级**

| 变更对象 | 典型频率 |
| --- | --- |
| Prompt 模板、编排流程、工具描述 | 每天数次 |
| 用户表结构、权限模型 | 每月一次 |

耦合的直接后果：每次微调 prompt 都要重新构建整个后端、重跑全量测试、重启服务。团队会因为「改 prompt 成本太高」而放弃优化，这是能力停滞的开始。

**（3）故障域必须隔离**

模型超时、Token 超限、工具执行异常、沙箱 OOM —— 这些是**高频**故障（日均数十次）。它们绝不能有任何机会影响认证、计费等核心链路。独立进程 + 独立部署单元是最彻底的隔离手段。

### 2.2 层间契约

| 边界 | 协议 | 约束 |
| --- | --- | --- |
| 接入层 ↔ 业务层 | HTTP/JSON + SSE | 统一响应体，JWT 鉴权 |
| 业务层 ↔ 智能层 | HTTP/JSON + SSE | **禁止共享数据库连接**，仅通过接口交互 |
| 智能层 ↔ 能力层 | 进程内调用 / MCP stdio / HTTP | 工具调用需带 traceId 与权限上下文 |
| 智能层 ↔ 数据层 | 仅 Redis（checkpoint）+ PG（向量） | **不直连 MySQL 业务库** |

**核心铁律**：
- 业务层 = 有状态的数据主人（拥有 MySQL 写权限）
- 智能层 = 无状态的计算单元（状态存 checkpoint，可随时被 kill 重启）

智能层不直连 MySQL 的理由：一旦 Python 侧能写业务库，事务边界、数据一致性、schema 变更协调会立刻变成跨语言噩梦。所有业务数据落库统一由 Java 侧负责，这是单一写入口原则。

### 2.3 为什么能力层要独立于智能层

MCP 工具、Skill 技能、执行沙箱这三者是**可被任意 Agent 复用的资源**，各自需要独立的：

- 注册与发现机制
- 版本管理与灰度
- 权限控制（哪个角色能用哪个工具）
- 调用审计与计费

如果硬编码进 Agent 引擎，就永远做不出工具市场和技能市场 —— 而这恰恰是 Agent 平台的护城河。独立成层后，新增一个工具是「注册一条记录」，而不是「改代码发版」。

## 三、技术选型与理由

### 3.1 前端

| 技术 | 版本 | 选择理由 | 为什么不选替代方案 |
| --- | --- | --- | --- |
| Vue 3 | 3.5+ | Composition API 逻辑复用强，团队上手快，中文生态完善 | React 心智负担更高（hooks 依赖数组、闭包陷阱），团队交付速度更重要 |
| TypeScript | 5.6+ | Agent 平台的消息/事件结构复杂且嵌套深，类型约束是刚需 | 纯 JS 在 SSE 事件类型爆炸后无法维护 |
| Vite | 6+ | 冷启动秒级，HMR 快 | Webpack 配置复杂、构建慢 |
| Pinia | 2+ | 官方状态库，TS 支持好，无 mutation 样板代码 | Vuex 已停止演进 |
| 原生 CSS + Design Token | — | 双主题切换用 CSS 变量最干净，零运行时开销 | Tailwind 在需要精细双主题时类名膨胀严重；组件库（Element Plus）风格固定，无法做出差异化视觉 |

> **重要决策**：不引入现成 UI 组件库。企业级平台的视觉识别度是产品资产，套用 Element Plus 会让产品看起来像后台管理系统。我们自建基础组件（约 15 个），配合设计 token 实现黑白双主题。

### 3.2 后端

| 技术 | 版本 | 选择理由 |
| --- | --- | --- |
| Spring Boot | 3.3.x | Java 17 基线，原生支持虚拟线程，Jakarta EE 命名空间 |
| MyBatis-Plus | 3.5.x | 复杂查询可控（Agent 平台有大量多条件分页与统计），代码生成省时 |
| Spring Security | 6.x | JWT + RBAC 标准实现，避免自己造轮子留安全漏洞 |
| Redisson | 3.3x | 分布式锁、限流器、延迟队列开箱可用 |
| Sa-Token（可选） | — | 若嫌 Security 配置繁琐可替换，v1 先用 Security 打基础 |

**架构形态：模块化单体起步**

```
backend/
├── agentforge-common      公共响应体、异常、工具类、常量
├── agentforge-auth        认证授权（用户、角色、权限、验证码）
├── agentforge-session     会话与消息（含 SSE 中继）
├── agentforge-capability  工具/技能注册中心、沙箱调度
├── agentforge-knowledge   知识库与 RAG 检索
├── agentforge-admin       运营后台（配额、审计、成本）
└── agentforge-boot        启动模块（唯一可执行 jar）
```

**为什么不直接上 SpringCloud**：

模块化单体在**接口契约层面**已经按微服务标准设计（每个模块对外只暴露 `api` 包下的接口，内部实现包禁止跨模块引用）。这样做的收益：

- 本地只需启一个进程，调试成本低，开发速度快 3 倍
- 没有分布式事务问题，先把业务逻辑跑对
- 拆分时机成熟时（P14 阶段），把模块提为独立服务只需改依赖注入方式为 Feign 调用

反过来，一开始就上 Nacos + Gateway + 6 个服务进程，前两周会全部消耗在环境问题上，且早期需求变动频繁时跨服务改接口的成本极高。

> **经验**：微服务是组织规模的解药，不是技术先进性的勋章。团队人数 < 10 人时，模块化单体几乎总是更优解。

### 3.3 Agent 引擎

| 技术 | 选择理由 |
| --- | --- |
| Python 3.11+ | LLM 生态事实标准，所有新框架首发 Python |
| FastAPI | 原生 async、自动 OpenAPI 文档、SSE 支持简洁 |
| LangGraph | 图状态机编排，原生支持检查点、中断恢复、人工介入（HITL） |
| LangChain | 只用其模型抽象层与工具协议，**不用它的 Chain/Agent 高层封装** |

> **关键取舍**：LangChain 的 `AgentExecutor` 等高层封装黑盒程度高、难以调试、版本变动大。我们只取它稳定的底层抽象（`BaseChatModel`、`BaseTool`、消息类型），编排逻辑全部用 LangGraph 显式定义。这样每一步状态流转都在自己代码里，出问题能定位。

### 3.4 数据层三库分工

| 库 | 职责 | 为什么必须是它 |
| --- | --- | --- |
| MySQL 8.0 | 用户、会话、消息、工具、技能、审计、配额 | 事务强一致，运维成熟，团队最熟；消息表将来分表方案成熟 |
| PostgreSQL 16 + pgvector | 向量索引、Embedding、混合检索 | 向量检索能力 MySQL 没有；pgvector 支持 HNSW 索引，且能与元数据在同一 SQL 中过滤（避免「先检索后过滤」的召回损失） |
| Redis 7 | 会话缓存、验证码、限流计数、分布式锁、LangGraph checkpoint | 内存级读写，天然过期语义 |

**为什么不用专用向量库（Pinecone / Milvus）**：
v1 数据量在千万级以内，pgvector 的 HNSW 完全够用，且省掉一个中间件的运维与数据同步成本。更重要的是 pgvector 支持在向量检索的同一条 SQL 里做元数据过滤（`WHERE tenant_id = ? AND doc_type = ?`），而独立向量库需要先检索再回表过滤，在强过滤场景下召回率会显著下降。数据量突破亿级时再迁移，届时接口层已抽象好。

**为什么不把向量也放 MySQL**：
MySQL 9 虽有向量类型，但索引能力与生态成熟度远不及 pgvector，且会让 OLTP 库承担高 CPU 的向量计算，影响业务查询稳定性。

## 四、关键链路设计

### 4.1 一次对话的完整流转

```
1. 前端 POST /api/v1/chat/stream          → 建立 SSE 连接
2. 网关：JWT 校验 → 用户级限流 → 注入 traceId
3. 会话服务：校验会话归属 → 检查 Token 配额 → 落库 user message
4. 会话服务：插入 assistant message 占位（status=streaming）
5. 调用 Agent 引擎 POST /run（内网，带 traceId + 用户上下文）
6. 引擎：加载 checkpoint → 组装上下文 → 调模型
7. 模型返回 tool_calls → 能力层执行（MCP / 沙箱）→ 结果回写 state → 再调模型
8. 每个 token 通过 SSE emit → Java 中继转发前端 + 增量缓冲落库
9. 结束：更新 assistant message（status=done）→ 扣减 Token 配额 → 写审计日志
```

### 4.2 为什么用 SSE 而非 WebSocket

| 维度 | SSE | WebSocket |
| --- | --- | --- |
| 协议 | 标准 HTTP，穿透企业代理无障碍 | 需协议升级，部分代理/网关拦截 |
| 断线重连 | 浏览器原生支持 + `Last-Event-ID` | 需自行实现 |
| 心跳保活 | 服务端发注释行即可 | 需实现 ping/pong |
| 适用场景 | 一次请求 → 长时间单向流 | 双向高频交互 |

Agent 对话完全符合 SSE 的语义模型。引入 WebSocket 会额外承担心跳、重连、状态机的实现与运维成本，收益为零。

**唯一注意点**：SSE 在 HTTP/1.1 下受浏览器同域 6 连接限制。解决方案是同一页面只维持 1 条 SSE 连接（多会话共用连接 + 事件里带 sessionId 区分），或部署 HTTP/2。

### 4.3 为什么 Java 要做中继而不让前端直连 Python

如果前端直连 Python：
- Python 需重复实现 JWT 校验与 RBAC → **两套鉴权逻辑必然漂移**，是安全事故经典源头
- Python 服务必须暴露公网 → 攻击面扩大
- 配额扣减、审计落库分散在两侧 → 数据口径不一致
- 未来换引擎（LangGraph → 自研）前端需要改造

中继的代价仅是一跳内网延迟（约 1-3ms），相对于模型首 token 延迟（500ms+）完全可忽略。

### 4.4 流式消息的落库时机

**错误做法**：等流结束后一次性落库。用户中途关闭页面 → 整轮对话丢失。

**正确做法（三段式）**：

| 阶段 | 动作 |
| --- | --- |
| 请求进入 | 同步落库 user message |
| 流开始 | 插入 assistant message，`status=streaming`，content 为空 |
| 流进行中 | 每 500ms 或累计 100 token，增量 UPDATE content（合并写，避免高频 IO） |
| 流结束 | UPDATE `status=done` + token 用量 + 结束时间 |
| 异常中断 | `status=interrupted`，保留已生成内容 |

这套设计同时是「继续生成」「重新生成」「历史回溯」三个功能的数据基础。

## 六、非功能性设计目标

| 维度 | 目标 | 手段 |
| --- | --- | --- |
| 性能 | 首 token < 1s；非流式接口 P99 < 200ms | Redis 缓存、连接池调优、异步落库 |
| 可用性 | 核心链路 99.9% | 故障域隔离、模型多供应商降级、熔断 |
| 安全 | 无高危漏洞 | 密码 BCrypt、JWT 双 Token、沙箱隔离、SQL 参数化、越权校验 |
| 可观测 | 任一请求可全链路追踪 | traceId 贯穿三语言、结构化日志、指标埋点 |
| 成本 | Token 用量可归因到人/会话/工具 | 计费中间件 + 用量看板 |
| 扩展 | 新增工具零代码 | MCP 协议 + 注册中心 |
